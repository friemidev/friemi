# Friemi v2.7 计划 Checklist

分支：`feature/v2-7-plan`

创建日期：2026-08-08

## 0. 版本目标

v2.7 重点处理移动端真实体验中的高频问题：阻断级崩溃和卡死、多人场景性能、狼人杀核心可玩性、图片上传兼容性、活动状态显示、搜索/消息/通知链路、Profile 和聚吧管理体验，以及移动端视觉减负。

本文件作为 v2.7 的执行清单。后续实现时，每完成一个 checklist 项就在本文档中勾选，避免只在 PR 描述里记录。

### 优先级定义

- `P0`：会导致页面崩溃、卡死、核心功能不可用、消息/通知丢失、多人房间明显不可玩的任务。
- `P1`：高频路径或关键业务能力，影响用户完成主要操作，但有绕路或临时替代方式。
- `P2`：视觉一致性、布局优化、交互效率和文案完整性。
- `P3`：发布收尾、版本公告、截图归档、非阻断测试补充。

### 按分区执行总览

| 分区 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 稳定性 / 性能 / 发布链路 | 13、19、20、25、35、40、41 | 1 | 全局验收 |
| 狼人杀工具 | 8、10、34、41 | 9、11、12 | 多人截图和录屏验证 |
| Profile / 社交关系 | 21、26 | 7、22、24、27、28、29、30 | 5、18、23 |
| 首页 / 搜索 / 活动 | 2 | 14、31、32 | 3、4 |
| 礼物 / 商城 | 16、17、33 | 15 | 礼物动效降级和视觉验收 |
| 聚吧 / 群聊 / 公告管理 | 36、37、39 | 6、38 | 管理弹窗视觉统一 |

### 建议执行批次

1. `P0-A 稳定性`：先修 `/profile/[profileId]` Prisma 报错、登录错乱、聊天室返回卡死、首次私聊丢消息、关注通知、在线离线状态。
2. `P0-B 多人性能和狼人杀核心`：同时分析全站并发卡顿，并修狼人杀多人房间布局/渲染、扫码/输入入房、法官角色视图。
3. `P1 高频路径`：处理图片上传、首页热门聚吧、搜索结果发消息、搜索返回、搜索卡片 UI、Profile 入口和备注名、礼物弹窗、聚吧删除/签到/公告删除。

## 1. 图片上传限制和格式扩展

### 原始需求

现在照片不能超过 4MB，这个限制有点太低了。新增多个种类的图片，尽量满足所有类型都可以上传，包括 gif。需要检查所有图片上传的接口。

### 初步检查范围

- `/api/uploads/activity-cover`
- `/api/uploads/direct-message-image`
- `/api/uploads/profile-avatar`
- `/api/uploads/moment-image`
- `/api/admin/top-news/upload`
- `ActivityCoverUpload`
- `MessageComposer`
- `ProfileAvatarPicker`
- `FootprintsMobilePage`
- `PlanetCoverUpload`
- `PlanetRoomComposer`
- `activity-cover-storage`
- 多语言上传文案：`apps/web/lib/copy.ts`

### 方案总结

统一图片上传能力，先在服务端建立一套共享的图片 MIME / 魔数检测 / 文件大小策略，再同步所有上传 API 和客户端 `accept`、大小校验、错误文案。目标是活动封面、头像、私聊图片、晒晒图片、星球图片、Top News 图片都使用一致的格式判断，不再出现某些入口支持、某些入口拒绝的情况。

建议把限制从当前 4MB 提高到更合理的上限，具体实现前按使用场景拆分：

- 普通图片：建议 10MB。
- GIF：建议 15MB 或 20MB，避免动画图天然体积更大导致不可用。
- 头像：可继续单独设较小上限，也可以提高到 8MB，但必须明确和文案一致。

### 预期结果

- 用户可上传 `jpeg / jpg / png / webp / gif / avif / heic / heif` 中可被服务端可靠识别和存储的格式。
- GIF 上传后不被错误压缩或误判，至少能按原文件存储和展示。
- 客户端提示、服务端校验、实际存储扩展名一致。
- 所有图片上传入口行为一致，错误信息明确。

## 2. 活动开始后的状态显示

### 原始需求

活动如果已经开始，就显示进行中。如果没有结束时间，直到当天 23:59 都显示进行中，不能刚开始就显示已结束。

### 方案总结

统一活动状态判断逻辑，避免列表、详情、创建入口预览、移动 lobby 使用不同的结束规则。核心规则：

- 当前时间早于 `startAt`：未开始。
- 当前时间大于等于 `startAt` 且早于结束边界：进行中。
- 如果 `endAt` 存在，结束边界使用 `endAt`。
- 如果 `endAt` 不存在，结束边界使用活动所在日期的 23:59:59。
- 当前时间超过结束边界后才显示已结束。

需要重点处理时区，Friemi 当前主场景是巴黎，应沿用现有活动浮动时间逻辑，避免 UTC 日期导致当天活动提前结束。

### 预期结果

- 没有结束时间的活动在开始当天不会刚开始就变成已结束。
- 进行中的活动在 lobby、活动列表、详情页、创建入口预览等位置显示一致。
- 跨天活动仍按 `endAt` 正常显示。

### Checklist

- [ ] 盘点所有使用 `getActivityDisplayStatus`、`getActivityTimeState`、手写结束判断的位置。
- [ ] 在活动状态工具函数中统一无 `endAt` 的当天 23:59 结束边界。
- [ ] 更新 lobby 移动列表状态显示。
- [ ] 更新活动列表状态显示。
- [ ] 更新活动详情状态显示。
- [ ] 更新创建入口活动预览状态显示。
- [ ] 补充无结束时间、当天已开始、跨天、有结束时间等测试用例。

### 验收标准

- [ ] 无 `endAt` 且当天已开始的活动显示进行中。
- [ ] 无 `endAt` 的活动到当天 23:59 后才显示已结束。
- [ ] 有 `endAt` 的活动继续严格按 `endAt` 判断。
- [ ] 相关测试覆盖通过。

## 4. 活动详情改为向上弹窗

### 原始需求

活动从页面变成向上的弹窗，不要到顶但要差不多 85%，有动效，从下到上。最上面可以向下滑关闭，然后内部页面可以滑动。

### 方案总结

把移动端活动详情做成 bottom sheet 体验：从列表点击活动后，在当前页面上方弹出详情面板，而不是完整跳转到新页面。弹窗高度约为视口 85%，顶部保留露出的背景和拖拽手柄；面板进入时从底部上滑，关闭时下滑退出。内部内容独立滚动，顶部区域支持下拉关闭。

为降低风险，桌面端仍保持现有详情页；移动端优先在 `/lobby` 和 `/activities` 的活动卡片入口试点。直接访问详情 URL 时仍需保留可访问页面，保证分享链接、刷新、SEO 和回退兼容。

### 预期结果

- 移动端从列表进入活动详情更轻，不打断浏览上下文。
- 弹层高度约 85%，不完全到顶。
- 弹层内容可滚动，顶部可拖拽下滑关闭。
- 浏览器返回、手动关闭、点击遮罩关闭行为清晰。

### Checklist

- [ ] 设计共享 `MobileBottomSheet` 或复用现有弹窗能力。

- [ ] 实现遮罩点击关闭。
- [ ] 实现内部滚动区，避免 body 背景滚动穿透。
- [ ] 保留详情 URL 的直接访问页面。
- [ ] 接入 `/lobby` 移动列表卡片。

- [ ] 验证浏览器返回和关闭弹层不会破坏列表滚动位置。

### 验收标准

## 8. 狼人杀扫码和输入加入房间问题

### 原始需求

狼人杀扫码进房间有问题，输入加入有问题，有的时候会出现截图中的客户端异常。

### 初步检查范围

- `/game-tools/werewolf`
- `/game-tools/werewolf/join/[code]`
- `/game-tools/werewolf/rooms/[roomId]`
- `WerewolfCreateRoomPanel`
- `WerewolfRoomOverview`
- `getWerewolfRoomByCode`
- `werewolfRoomActions`
- `globalQrScanner`
- Android 原生扫码桥接逻辑

### 方案总结

把狼人杀加入链路拆成两条完整排查：扫码加入和手动输入房号加入。扫码侧需要确认二维码内容、URL 解析、Android 原生扫码事件、Web 摄像头扫码、房号 normalize 都能稳定得到同一个 room code。手动输入侧需要确认输入为空、大小写、空格、短横线、无效房号、已开局房间、已结束房间、用户已有活跃房间、游客 memberToken 等边界不会触发客户端异常。

截图中的 `Application error: a client-side exception has occurred` 必须当作 P0 bug 处理：加入失败可以显示错误页或提示，但不能白屏。

### 预期结果

- 扫码后稳定进入对应狼人杀房间或显示可理解错误。
- 手动输入房号稳定进入对应房间或显示可理解错误。
- 无效状态不会产生客户端白屏。
- Android App WebView、移动浏览器和桌面浏览器行为一致。

### Checklist

- [ ] 复现截图中的客户端异常，并记录触发路径。
- [ ] 检查二维码生成内容是否始终是 `/game-tools/werewolf/join/[code]`。
- [ ] 检查 `getWerewolfRoomCodeFromScan` 对完整 URL、相对 URL、纯房号的解析。
