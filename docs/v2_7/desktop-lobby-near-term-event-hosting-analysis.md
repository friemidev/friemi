# `/lobby` 网页端“临近活动转聚吧”方案分析

## 1. 目标与范围

目标是在网页端 `/lobby` 中补充近期有参与价值、但尚无人组局的公开活动。候选活动可以直接显示在聚吧列表，但不显示报名人数；用户点击卡片后先查看详情弹窗，再在详情页面创建真实聚吧。这样可以增加聚吧内容密度，也减少用户必须先去活动页寻找内容的步骤。

本阶段只做分析，不修改功能。后续实现应满足：

- 仅改变桌面网页端 `/lobby` 的数据和卡片操作。
- 不改变当前移动端 `/lobby` 的布局、标签、列表密度和交互。
- 已经存在对应聚吧的活动不能重复创建。
- 待创建活动不能伪造报名人数、房主或群聊状态。
- 第一个完成创建的用户成为房主，创建过程必须并发安全。

## 2. 当前系统已经具备的能力

### 2.1 活动与聚吧是两类数据

- `PublicEvent` 是外部或平台导入的公开活动信息。
- `Activity` 是用户可以报名、聊天和管理的聚吧。
- `Activity.publicEventId` 可以把聚吧关联到来源活动。

### 2.2 网页端卡片已有“从活动发起聚吧”的入口

`ActivityCard.tsx` 已区分活动信息卡和聚吧卡。活动信息卡的主操作目前是“去聚聚”，可以进入发起流程；桌面卡片还提供双操作区域。

这说明卡片层不需要重新设计一套模型。候选活动卡保持现有聚吧列表的外观和点击方式，但隐藏人数；创建入口放在详情页面，而不是列表卡片上。

### 2.3 已存在自动生成和认领聚吧的代码

项目已有以下能力：

- `autoCreateTeamsFromHotActivities.ts`：从热门 `PublicEvent` 自动创建 `Activity`。
- `claimAutoCreatedActivity.ts`：登录用户认领自动生成的聚吧。
- `ClaimAutoCreatedActivityButton.tsx`：详情页认领按钮。
- `ActivitySourceLink.sourceUrl`：具备唯一约束，可用于防止同一来源重复创建。

当前规则是最近 7 天内浏览量大于 1、收藏数大于 0，每天最多生成 3 个，认领窗口为 24 小时。

## 3. 当前方案不能直接扩大的原因

### 3.1 自动生成任务实际上没有生产调度

接口 `/api/cron/auto-create-teams-from-hot-activities` 已存在，但根目录 `vercel.json` 的 `crons` 未包含该接口。因此该能力除非被外部任务手动调用，否则不会稳定运行。

### 3.2 当前认领操作存在并发覆盖风险

现有逻辑先读取活动，再按 `id` 更新 `organizerId`。两个用户几乎同时点击时，都可能通过读取阶段，后一个更新可能覆盖前一个用户。

扩大入口之前必须改为以下任一方式：

- 推荐：点击时原子创建聚吧，使用唯一来源键保证只有一个请求成功；失败请求查询已创建聚吧并跳转。
- 备选：保留预创建聚吧，但使用带原房主条件的 `updateMany` 或数据库行锁认领，更新数量为 `0` 时视为已被别人认领。

### 3.3 预创建会产生“系统假房主”语义

`Activity.organizerId` 目前必填，所以自动生成时先挂在 Friemi 或管理员账户下。用户在列表里可能误以为已经有人负责，且聚吧数量、房主信息和通知归属容易产生歧义。

### 3.4 “临近”不能只按时间判断

把所有近期活动塞入聚吧会造成信息污染。没有准确地点、时间已过、重复活动、质量较差或报名入口失效的内容都不适合成为候选聚吧。

## 4. 推荐方案：列表展示候选活动 + 详情页创建聚吧

不提前创建 `Activity`。桌面网页端 `/lobby` 查询合格的 `PublicEvent`，以“待创建聚吧”的内容卡混入聚吧列表。点击卡片只打开现有详情弹窗；用户在详情页面明确点击“创建聚吧”后，系统才创建对应 `Activity`，该用户成为真实房主。

### 4.1 候选活动条件

建议首版使用明确而保守的条件：

- `status = SCHEDULED`、`visibility = PUBLIC`。
- 结束时间尚未过去；无结束时间时开始时间尚未过去。
- 开始时间位于未来 2 小时至 14 天。
- 城市、地址和开始时间完整。
- 不存在同一 `publicEventId` 的进行中聚吧。
- 不展示取消、私密、已结束或票务链接已明确失效的活动。
- 真实且进行中的聚吧数量不足一页时，用候选活动补足内容。
- 候选活动可以继续出现在后续分页，但不能排在进行中的真实聚吧之前。

候选排序可使用：时间临近度、收藏、详情浏览、分类多样性和数据完整度。第一版不建议使用复杂推荐算法。

### 4.2 卡片展示与交互

- 候选活动沿用当前列表卡片的图片、标题、分类、时间、地点和点击方式。
- 不显示 `0 人`、`0 / N` 或头像，因为它还不是实际聚吧。
- 可增加低干扰的“待组局”状态文字，用于区分真实聚吧，但不增加新的浮动按钮。
- 点击卡片后打开详情弹窗，列表本身不执行创建操作。
- 详情页面显示“创建聚吧”主按钮，并说明创建后当前用户将成为房主。
- 未登录用户在详情页面点击创建后先登录，登录完成回到同一详情。
- 创建成功后进入新聚吧详情；其他用户再次打开候选时，应看到真实聚吧入口。
- 若其他用户抢先创建，则不再创建第二个聚吧，直接跳转到已经存在的聚吧并提示“已有用户发起该聚吧”。

### 4.3 列表优先级

推荐按以下层级排序，而不是把候选活动和真实聚吧使用同一个分数混排：

1. 与当前用户有关的进行中真实聚吧，例如本人创建、已报名或好友参与。
2. 其他 `RECRUITING`、`CONFIRMED` 的进行中真实聚吧。
3. 尚未创建聚吧的近期候选活动。
4. 已结束或已取消的真实聚吧。

这样能保证真实、可参与的聚吧始终优先，同时避免历史聚吧把仍有时效性的候选活动压到列表底部。候选活动内部再按开始时间、距离、收藏和浏览热度排序。

### 4.4 原子创建与去重

推荐事务流程：

1. 校验 `PublicEvent` 当前仍可用。
2. 查询是否已有进行中的关联聚吧；有则直接返回其 `id`。
3. 用户在详情页确认创建后，创建 `Activity`，`organizerId` 直接使用当前用户。
4. 同事务写入唯一来源键，例如 `desktop-lobby-claim:{publicEventId}`。
5. 唯一键冲突时回滚本次创建，再读取赢家创建的聚吧并返回。

现有 `ActivitySourceLink.sourceUrl @unique` 可以承担首版并发互斥，不必立即修改数据库结构。后续如允许同一活动按不同日期或场次多次组局，应把唯一键扩展为 `publicEventId + session/startAt`。

## 5. 保证移动端 UI 不变

当前页面已经根据请求设备分流：移动端使用 `getMobileActivityLobbyPage` 和 `MobileLobbyV23View`，桌面端使用 `ActivityLobbyView`。

后续实现应遵守：

- 候选 `PublicEvent` 只加入桌面端 `ActivityLobbyView` 的数据参数。
- 不修改 `MobileLobbyV23View`、`MobileActivityListRow` 和移动端分页数量。
- 不把候选写进通用 `getOpenLobbySection`，否则移动端和 API 也会收到它们。
- 为桌面候选单独建立查询函数和组件属性，避免依赖 CSS 隐藏来区分设备。

## 6. 数据同步与生命周期

- 来源活动取消后，尚未创建的候选立即消失。
- 来源活动时间或地点变更时，未开始的关联聚吧需要明确同步策略；建议只同步尚无参与者、且房主未编辑过的信息。
- 房主创建后，活动卡从“待组局”替换为真实聚吧卡，并开始显示真实人数和报名状态。
- 无人报名且已结束的聚吧按现有归档逻辑处理，不应每日重复生成。
- 房主应在确认前看到职责说明，包括信息维护、申请审核和群聊管理。

## 7. 建议实施顺序

1. 新增桌面候选查询及单元测试，验证时间范围、质量过滤和去重。
2. 新增详情页原子创建服务，补两个用户同时点击的并发测试。
3. 桌面 `ActivityLobbyView` 按优先级混入候选卡；移动端代码不改。
4. 增加埋点：候选曝光、点击、创建成功、并发转入已有聚吧、创建后报名人数。
5. 先灰度一周，再决定是否扩大 14 天窗口或首屏候选数量。

## 8. 验收指标

- 同一来源活动始终最多有一个自动认领生成的进行中聚吧。
- 并发点击不会覆盖房主。
- 移动端 `/lobby` 的截图、DOM 结构和每页 8 条保持不变。
- 桌面候选卡详情打开率和详情页创建成功率可观测。
- 候选创建后 7 天内的报名率高于普通空聚吧，且用户隐藏/跳过率没有明显上升。

## 9. 结论

该方向可行，而且比预先生成空聚吧更符合当前产品结构。推荐采用“聚吧列表展示候选活动、隐藏人数、点击查看详情、详情页创建真实聚吧”，并保证进行中的真实聚吧拥有最高优先级。这样能增加有效内容，又不会制造虚假人数、假房主或无主群聊，同时可以明确隔离移动端 UI。
